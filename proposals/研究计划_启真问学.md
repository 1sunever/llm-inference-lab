## 2. 背景与问题

我的实验机是一张 RTX 4050 Laptop：6.0 GB 显存、20 个 SM、sm_89（`results/flash_attn_bench.json` 的 `env`）。这个数字几乎单独决定了技术路线：Qwen2.5-1.5B（fp16）加载后就占掉 2.876 GB（`results/spec_speedup.json` → `data.real_model.vram_after_load_gb`），剩下 3 GB 要同时装激活、临时缓冲和 KV。按 28,672 B/token 的 KV 开销算（`results/paged_fragmentation.json` → `data.config.kv_bytes_per_token`），2.9 GiB 只对应 108,602.5 个 token（同文件 `budget_tokens`）。**在这个预算里能同时放几条序列，是整个系统唯一的自由度。**

所以三件事在这里不是可选项：

**第一，KV 怎么分配。** 同样 2.9 GiB，按 `max_len` 连续预分配能并发 26.5 条序列，分页（block_size=16）能并发 133.1 条，浪费率 80.09% → 0.89%（`results/paged_fragmentation.json` → `data.rows`，5.02×）。差距不在 attention 快不快，而在分配器：不换它，卡上只剩不到四分之一 batch 可用，后面所有吞吐讨论都无从谈起。文献基线（非本仓库实测）也承认这笔账是负的：vLLM 论文 §7.1 报告分页使 attention kernel 延迟升高 20–26%，靠更大 batch 摊平。

**第二，重复的 prefill 要不要付。** 多轮对话里同一段 1024 token 的 system prompt 会被反复 prefill。实测 4 会话 × 4 轮下前缀命中率 82.32%，省掉 19,072 / 23,168 个 prefill token（`results/paged_prefix.json` → `data.rows[0]`）。这张卡的 prefill 算力本就不宽裕：N=4096 causal 只跑到 19.46 TFLOP/s（`results/flash_attn_bench.json` → `data.rows[8].triton_tflops`）。更要紧的是池子大小：4096 块和 512 块的命中率完全相同（都是 82.32%），压到 128 块才掉到 78.59% 并出现 122 个装不下的块。**瓶颈是驱逐与调度策略，不是容量**——这决定了该往哪里加资源。

**第三，一次前向能不能多换几个 token。** decode 是访存瓶颈，6 GB 卡的带宽决定单请求 token/s 的上限。实测 k=5 的验证前向 56.26 ms，是单 token 前向 49.80 ms 的 1.13×（`results/spec_speedup.json` → `data.real_model.forward_cost`）——多验 4 个 token 只贵 13%，这是这张卡上"用带宽换吞吐"的唯一出口。但同一套 k=5 参数，在重复性 prompt 上端到端是 1.27×（三轮均值），在开放 prompt 上只有 0.89×（`data.real_model.runs`）。**收益的正负取决于文本，而系统里 k 是常数——这个错配就是本计划的起点。**

## 3. 已完成的工作

四个模块都是我自己写的，数字来自 `results/*.json` 的本机实跑（RTX 4050 6 GB / Triton 3.7.1 / torch 2.13.0），共同作用是证明我能把"哪一层是瓶颈"说清楚，而不是只会调包。

**FlashAttention（Triton，仅前向）。** N=2048、D=64、causal 下，朴素实现的中间量要 532.0 MB，我的实现只要 4.125 MB，129.0×（`results/flash_attn_bench.json` → `data.memory`）；N=4096 时朴素实现直接 OOM，我的实现 1.765 ms 对 SDPA 的 1.791 ms，1.01×（`data.rows[8]`）。**这证明在这张卡上 FlashAttention 的决定性收益是显存而非速度**：短序列（N=256，0.081 对 0.052 ms）仍落后 37%，原因是 launch 开销与 tile 利用率——这条写进了"局限"，没藏起来。

**分页 KV 管理（块表 + 引用计数 + 链式哈希 + LRU 驱逐）。** 碎片 80.09% → 0.89%，并发 26.5 → 133.1（`results/paged_fragmentation.json`）；分页分配量 210,656 token 对实耗 208,775，多出的 1,881 恰是 256 条序列各自的最后一块，与"平均浪费半块"对得上。**这证明 PagedAttention 的价值在分配器，而且这笔账能用算术核对，不需要"大约"**。

**Paged decode kernel（Triton，按 block_table 直接读）。** ctx=2048 时 fused 0.244 ms 对 gather+SDPA 的 1.029 ms（4.22×），ctx=256 时 11.28×（`results/paged_decode.json`）；三条独立路径（fused / gather / 纯 fp32 参考）最大绝对误差 2.96e-4（`results/paged_correctness.json` → `data.fused_vs_ref`）。**这证明零拷贝的收益随上下文变长单调衰减（11.28× → 4.22×）**，因为 gather 那次搬运的占比在下降；也就是说长上下文下剩下的空间不在"少搬一次"，而我没找到它。

**投机解码（拒绝采样 + 残差修正 + 树状草稿 + tree mask）。** 实测接受率 0.69935 对理论 0.70000，输出分布 L1 距离 0.0038、χ²=4.15（7 dof，0.05 临界值 14.067）；对照"直接接受草稿不验证"的 L1 是 0.6005、最大偏差 0.2000（`results/spec_correctness.json`）。速度侧，54 组 (α, cost_ratio) 网格里 53 组的最优 k 严格小于 k 上限，α=0.9 / cost_ratio=0.05 时 k_opt=13、峰值 4.674×（`results/spec_speedup.json` → `data.optimal_k`、`data.knee_summary`），蒙特卡洛与理论公式的最大相对误差 0.0036。**这证明验证算法可以做到分布无损，而"k 取多少"完全取决于 α 与单步成本——这两个量我目前都当常数，正是下一个课题要拆掉的东西。**

**MoE 层（pad 成 `[E, cap, D]` + 一次 bmm）。** batch=1 时一次前向发出 48 个 kernel，等参数量 dense 只有 6 个；延迟 1.036 ms 对 0.256 ms（慢 4.05×），其中路由单独 0.391 ms、占 24.3%（`results/moe_routing.json` → `data.kernel_counts`、`token_sweep[0]`、`batch1_breakdown_ms`）；N=512 时反超 2.29×（`token_sweep[5]`）。容量机制上，dropless 时 71.4% 的槽位是零 pad 却照样进 bmm，38.78 ms 对有容量限制的 9.42 ms（`results/moe_balance.json` → `data.experiment_b.rows`）。**这证明小 batch 下 MoE 是 launch 与 padding 受限，不是算力受限**——一个与主流叙事相反的结论。

## 4. 想在项目里继续做什么

三个候选课题都从上面某一条"没做到"里长出来，不换话题。

### 课题一（主线）：paged decode kernel 的 block_size × GQA 联合优化

**问题陈述。** 现有 kernel 有三处硬编码：block_size 固定 16、KV 头数等于 Q 头数（无 GQA）、一个 program 只管一个 (batch, head)，grid = B×H。加速比从 ctx=256 的 11.28× 衰减到 ctx=2048 的 4.22×，说明"省掉那次拷贝"的收益已被吃干，剩下的成本是**每个 (b, h) 把同一段 K/V 完整读一遍**。4 个 Q 头共享 1 组 KV 时读取量应降到 1/4；但 block_size 调大以减少页表长度，又会抬高最后一块的浪费（bs=16 实测 0.89%）。两者耦合，公开材料里没有针对这一组合的系统扫描。

**技术路线。** (a) 按 KV 头分组：一个 program 处理 G 个 Q 头，K/V tile 只读一次进 SRAM，G 个 query 复用；(b) block_size 做成 constexpr，扫 {8, 16, 32, 64}；(c) 正确性沿用三路交叉验证；(d) 碎片率用现有 lognormal 分布（mean 815.53、max_len 4096）逐 block_size 重算，把延迟与浪费率放进同一张表做联合选择。

**可验证的成功指标。** ctx=2048、B=8 下延迟从 0.244 ms 降到 ≤0.183 ms（−25%）；GQA 4:1 时三路最大绝对误差 ≤3e-4（沿用现有 2.96e-4）；block_size=32 时碎片浪费 ≤2.0%；端到端并发不低于 133.1 的 0.95×。

**为什么现在做不了、需要项目什么。** kernel 部分这张卡能跑，"接进真实引擎做端到端"不能：Qwen2.5-1.5B 加载已占 2.876 GB，余量还要同时放引擎运行时、激活与 KV，长上下文下并发上不去，"并发提升"会被显存上限压平，测不出 kernel 的真实贡献。我需要至少一张 24 GB 级卡，纯 kernel 与离线模拟器我自己做完。

### 课题二：接受率的可预测性——用草稿侧信号动态决定 k

**问题陈述。** 现在 k 是常数（3 或 5），但实测接受率随文本类型差 20 倍：散文段每次前向只产出 1.042 个 token（接受率 0.044），代码段 3.5 个（0.915）（`results/spec_speedup.json` → `data.workload_prompt_lookup.by_segment`）；端到端同一个 k=5，重复性 prompt 1.27×、开放 prompt 0.89×（`real_model.runs` 的均值）。理论侧同样不等距：54 组 (α, cost_ratio) 网格里 53 组的最优 k 严格小于 k 上限，k_opt 在 0–21 之间散开（0 等于"不如不投机"），峰值加速比 1.00×–4.67×。**也就是说"k 取多少"随文本与单步成本漂移，而现在把它写死了。**

**技术路线。** (a) 用草稿侧便宜信号在线估 α：匹配的 n-gram 长度、最近 W 步滑动接受率、命中率，三者都不需要额外前向；(b) 成本模型换成这张卡上的实测曲线（1 token 49.80 ms，k=5 56.26 ms，见 `forward_cost`）；(c) 每步解 argmax_k (tokens_per_step / cost)，与固定 k=3、k=5 三方对照；(d) 以 oracle k 为上界，量出预测误差本身。

**可验证的成功指标。** 2000 token 混合 workload 上 tokens/step 从 2.366（k=3）提到 ≥2.9，同时不劣于 k=5 的 3.074 的 0.95×（即 2.92）；端到端 ≤24.1 ms/token（相对 30.13 ms/token 基线的 1.25×）；k 与 oracle 的平均绝对误差 ≤1；开放段不再出现 <1.0× 的负收益。

**为什么现在做不了、需要项目什么。** 需要**稳定的计时**：同一配置三轮之间加速比从 1.27× 到 1.58×（`reps_speedup_spread` 最大 1.854），GPU 温度 72–84 °C、功耗 30.7–65.8 W（`moe_routing.json` / `moe_balance.json` → `gpu_clock_*`），笔记本在节流，端到端百分比可能只是噪声。我需要一段可独占、可固定时钟的机器时间，否则这个课题的数字不可比，我也不会拿它当结论。

### 课题三：MoE batch=1 的 launch-bound——grouped GEMM 能否救回来（12 周内只写方案，不交付）

**问题陈述。** N=1 时 48 个 kernel 对 6 个，单次 launch 间隙实测 33.70 µs（min 口径 13.01 µs，见 `launch_gap`），光这一项就是几百 µs；路由单独 0.391 ms。现有实现用"pad 成 `[E, cap, D]` + 一次 bmm"换掉 per-expert 循环，代价是 dropless 时 71.4% 的行是零行、照样进 bmm。

**技术路线。** gate + softmax + topk + 容量掩码合进一个 kernel；用 variable-M 的 grouped GEMM（按 expert 前缀和切 tile，M 可小到 1）替掉 pad-bmm；剩余 launch 用 CUDA graph 消掉。

**可验证的成功指标。** N=1 的 kernel 数 48 → ≤12；延迟 1.036 ms → ≤0.51 ms（等参数量 dense 是 0.256 ms，目标不超过它的 2×）；N=512 保持 ≥2.29× 不回退；dropless 的 padding 计算占比从 71.4% 降到 ≤10%。

**为什么现在做不了、需要项目什么。** 现在只能跑 dim=512 / hidden=1024 / E=8 的玩具层（峰值 548.55 MB，`moe_routing.json` → `peak_memory_mb`）。真实 MoE 的 E 是 64–128、权重几十 GB，6 GB 装不下；"E 到 64 以上时 tile 划分还成不成立"必须多卡才能问。所以 12 周里只写方案、不交付，避免承诺我无法验证的东西。

## 5. 与浙大 AI Infra 方向的契合

只谈技术层面，不谈人。

**KV 管理。** 我有一份能跑的分配器：块表、引用计数、写时复制、链式哈希、LRU 驱逐，并用 80.09% → 0.89% 这笔账验证过。课题一要动的 `block_size` 是 KV 管理里最核心的权衡——分配粒度同时决定碎片率、页表长度和 kernel 效率，三者互相拉扯。

**调度。** 前缀缓存的驱逐策略比容量更重要（512 块与 4096 块命中率相同）；容量因子在 MoE 里同时是"丢 token 的规则"和"kernel 缓冲区的上限"（dropless 反而最慢，38.78 对 9.42 ms）。课题二的 k 选择本质也是调度：每步该分配多少验证算力。

**算子优化。** 我写过 Triton 的 FA2 前向、paged decode 和配套三路交叉验证。我不追求"比 cuBLAS 快"，追求"能解释每一版的瓶颈"——N=4096 追平 SDPA 但 N=256 落后 37%，原因是 launch-bound 加 tile 利用率不足。

三块是一条链：显存决定 batch，batch 决定 kernel 形状，kernel 形状决定单步成本，单步成本决定 k。我希望在项目里把这条链打通，而不是各做一段。
