# MoE：参数量与计算量解耦之后，代价跑到哪里去了

> 结论先行：MoE 在 **batch=1（decode）时是亏的**——本实现比等参数量 dense 慢 4.05×，
> 比等算力 dense 慢 8.5×。到 N=2048 才反超等参数量 dense（3.37×），
> 但**始终打不过等算力 dense**（0.78×）。
> 这不是实现太糙，是 MoE 的结构性特征：它省的是**权重读取**，不是**算力**。

---

## 1. 它到底省什么

Mixtral 8×7B 的账：47B 总参数，每 token 只激活 13B。论文 §3 说得最清楚：

> "the active parameter count … is **directly proportional to the inference
> compute cost**, but does not consider the memory costs" /
> "The memory costs for serving Mixtral are proportional to its **sparse
> parameter count, 47B**"

工程语言：**显存按 47B 算，算力按 13B 算**。于是 MoE 的性价比完全取决于
你处在哪个瓶颈：

| 场景 | 瓶颈 | MoE 表现 |
|---|---|---|
| decode，batch=1 | kernel launch + 随机访存 | **亏**（路由与 gather 的固定成本摊不掉） |
| prefill / 大 batch | 算力 | **赚**（同样 FLOPs 带更多参数） |
| 显存受限（6 GB 卡） | 容量 | **亏**（47B 权重根本放不下） |

本机实测把第一行与第三行都验证了。

## 2. 机制与三个真实的坑

代码在 `src/llm_lab/moe/router.py`、`layer.py`。

### 2.1 路由

```
logits = x W_g            # (T, E)
probs  = softmax(logits)  # fp32：fp16 下 top-k 的次序可能因舍入翻转
top_k 个专家，权重按这 k 个 prob 归一化
```

**归一化这一步值得说**：Switch 用 top-1，不需要归一化；Mixtral / GShard 用 top-2，
不归一化时两个专家权重之和可能大于 1，等效于放大 FFN 输出。它改的是数值尺度，
不改路由决策。

### 2.2 容量因子：`capacity = ceil(N/E × CF)` 的陷阱

这是实现时真正踩到的坑，也是三组实验里最有价值的一条。

GShard 的容量按"每专家平均收到多少 token"定。但 top-k=2 时每个 token 占 **2 个**
槽位，每专家平均收到的是 `N·k/E`，不是 `N/E`：

```
capacity = ceil(N / E × CF)        # 照这个写
实际需求 = N × k / E                # top_k=2 时是它的 2 倍
```

`N=4096, E=8, k=2, CF=1.0` → capacity = 512，而平均每专家要接 1024 个 token，
**即使路由完全均匀也会丢掉一半**。实测（给 expert 0 的 logit 加 +2.0 制造热点）：

| CF | dropless | capacity | 丢弃率 | 有效 token | 零 pad 占比 | 单次耗时 |
|---|---|---|---|---|---|---|
| 1.0 | False | 512 | **78.25%** | 21.75% | 0.0% | 9.42 ms |
| 1.25 | False | 640 | 71.46% | 28.54% | 0.2% | 11.19 ms |
| 1.5 | False | 768 | 68.53% | 31.47% | 12.35% | 12.28 ms |
| 2.0 | False | 1024 | 62.48% | 37.52% | 31.24% | 14.30 ms |
| 1.0 | **True** | 512 | 0% | 100% | **71.40%** | **38.78 ms** |

这张表把 MoE 的核心 trade-off 摆全了，三条读法：

1. **丢弃主要来自容量公式，不是不均衡。** 全程 `max_load_ratio` 稳定在 3.42–3.51，
   而丢弃率从 78% 到 62%——不均衡程度没变，变的是容量。这两件事常被混为一谈。
2. **容量因子是把双刃剑**：CF 从 1.0 升到 2.0，丢弃率降 16 个点，
   但代价是零 pad 从 0% 涨到 31%（算了没用）且耗时涨 52%。
3. **dropless 不是免费的**。丢弃率归零，但 71.4% 的槽位是零 pad 却照样进 bmm，
   耗时 38.78 ms 是 CF=1.0 的 **4.1 倍**。"不丢 token"换来的可能是更差的吞吐。

GShard 原文用 `2N/(G·E)`，那个 2 正是把 top-k 计入。**照抄公式而不理解因子，
就会出现"看起来在跑、其实丢了一大半"的结果。**

### 2.3 aux loss：有效，但不是零成本

Switch 的负载均衡损失：

```
aux = α · E · Σ_i (f_i · P_i)
f_i = 被路由到专家 i 的 token 比例   ← argmax 统计，不可导
P_i = 平均 gate 概率                ← 可导
```

关键：`f_i` 是统计量，`argmax` 无梯度，**梯度只经 `P_i` 传播**。所以行为是渐进的：
先推高冷门专家的平均概率，下一轮 `argmax` 才真的把 token 换过去。

实测（300 步，E=8，top-1，初始把 expert 0 的 logit 固定 +3.0 制造塌缩）：

| aux_weight | 初始 max_load_ratio | 末 10 步均值 | 最终任务 loss |
|---|---|---|---|
| 0.0 | 7.39 | **7.80**（无救） | 1.59e-4 |
| 0.01 | 7.16 | **1.03** | 2.14e-3 |
| 0.1 | 6.33 | 1.01 | 1.91e-3 |

`E=8` 时 `max_load_ratio` 的理论上界就是 8，7.80 几乎是彻底塌缩。
`α=0.01` 就足够拉平。

**但任务 loss 从 1.59e-4 涨到 2.14e-3（约 13 倍）——aux loss 不是免费的。**
这是我这组实验里唯一一个"和预期相反"的发现：负载是拉平了，代价是模型拟合变差。
绝对值仍很小（这个小任务本身容易拟合），但它提醒：**均衡与拟合存在张力，
不能默认 aux loss 白送。**

## 3. 为什么 batch=1 时 MoE 更慢

配置：dim=512, hidden=1024, E=8, top_k=2, fp32，本机实测。

| N（token 数） | MoE | 等参数量 dense | 等算力 dense | vs 等参数 | vs 等算力 |
|---|---|---|---|---|---|
| 1 | **1.036 ms** | 0.256 ms | 0.121 ms | 0.247× | 0.117× |
| 512 | 2.259 ms | 5.165 ms | 1.190 ms | **2.29×** | 0.53× |
| 1024 | 3.876 ms | 10.646 ms | 1.914 ms | 2.75× | 0.49× |
| 2048 | 6.092 ms | 20.507 ms | 4.749 ms | **3.37×** | 0.78× |

参数账（同一次实验统计）：MoE 总参数 12.59 M，每 token 激活 3.15 M，
**稀疏度 75.0%**，FLOPs 只有等参数 dense 的 25.0%。

batch=1 时慢 4.05×，开销来源三处，全部实测：

1. **kernel 数量**：一次前向 **48** 个 CUDA kernel，等参数量 dense 只有 **6** 个。
   单次 launch 间隙最小口径 **13.0 µs**（链式 add 的斜率；中位口径 33.7 µs，
   受机器噪声影响大，取保守的最小值）。K=1 时每个 MoE kernel 只处理 1 个 token，
   算术量小到完全被 launch 吞掉。
2. **gather/scatter**：token 要散射进 `[E, capacity, dim]` 槽位再收回，
   随机全局访存，没有合并访存的机会。
3. **路由固定成本**：把路由与专家计算分开计时，路由单独 **0.391 ms**，
   占整层 **1.606 ms** 的 **24.3%**；它几乎与 token 数无关。

N=2048 时反超等参数 dense **3.37×**——MoE 省的是权重读取量，只有 kernel 被喂饱、
权重读取成为主项时这笔账才占主导。

**但始终打不过等算力 dense（0.78×）。** 这句话很重要：MoE 用 E 倍显存换来的
是"在这些 token 上追平一部分算力"；真要省算力得靠更大 batch 或 expert 并行
把权重摊到多卡。**单卡上 MoE 的收益有上限。**

## 4. 两个实现细节

**(a) kernel 数与 E 解耦。** E 从 2 扫到 32，kernel 数恒为 56（含 aux loss 的 8 个）。
原因是没有写 per-expert 的 Python 循环，而是 `index_add` + 一次 `bmm`
（多余行 pad 填零）。代价是 E 越大 pad 越多，收益是 launch 次数不随 E 增长。

同一组数据里 E 的影响（N=128）：

| E | MoE | 等参数 dense | 比值 | kernel 数 |
|---|---|---|---|---|
| 2 | 2.587 ms | 0.189 ms | 0.073× | 56 |
| 8 | 3.116 ms | 1.819 ms | 0.584× | 56 |
| 32 | 5.718 ms | 6.083 ms | 1.064× | 56 |

E 越大越划算，因为对照的 dense 参数量随之暴涨，而 MoE 的耗时增长慢得多。
这是 MoE "用显存换算力"最直观的一条曲线。

**(b) `index_add` + bmm 的代价**就是 §2.2 表里那 71.4% 的零 pad：
dropless 时所有槽位都进 bmm，其中七成是空转。这正是 DeepSeek 系要用
grouped GEMM 的动机——真解是让硬件支持变长分组矩阵乘，
而不是靠 pad 浪费或 Python 循环堆 launch。本仓库没有实现 grouped GEMM。

---

## 5. 局限

- **没有 grouped GEMM**。用 pad + 单次 bmm 替代，dropless 时 71.4% 的槽位空转。
- **没有 expert 并行**。单卡 6 GB，`all-to-all` 无从谈起，只做单卡行为。
- **fp32 跑的实验**。softmax 强制 fp32 以避免 top-k 次序翻转，但整体仍是 fp32 基准。
- **等算力 dense 的对照不完美**：用 hidden 维缩放对齐 FLOPs，只对齐了计算量，
  没对齐访存模式，故"MoE 不及等算力 dense"的差距可能被高估或低估。
- **aux loss 实验规模很小**（dim=64, 300 步）。它证明了方向与代价，不能外推到
  大模型的收敛速度。
- **launch 间隙的两个口径差 2.6 倍**（13.0 µs 最小 vs 33.7 µs 中位），
  说明该测量对机器负载敏感；我引用最小值并在正文标明，避免夸大 launch 成本。
