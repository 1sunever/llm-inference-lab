# 面试问答：每条都能指回仓库里的数字

> 用法：不要背结论，背**推理路径**。面试官追问的从来不是"是什么"，而是
> "你怎么知道""换台机器还成立吗""你试过什么不行的方案"。
> 下面每条的「证据」列指向本仓库的具体文件/字段，答不上来时能说"这个数在我仓库里，
> 我记的是 XXX 量级"就已经赢了一半。

## 一、FlashAttention

**Q1. FlashAttention 为什么快？**
不是少算，是少搬。朴素实现要把 N×N 的 S 和 P 写回 HBM 再读出来，
HBM 流量 O(N²)；FA 把序列切块在 SRAM 里做 online softmax，中间量从不落 HBM，
流量降到 O(N²/M)。算术强度从 ≈1 FLOP/byte 抬到 ≈N，才跨进 compute-bound。
**证据**：`docs/01_flash_attention.md` §1 的强度表；`results/flash_attn_bench.json` 的 `ai_flash`/`ai_naive`。

**Q2. 那在你的卡上快了多少？**
长序列持平（N=4096：1.765 vs SDPA 1.791 ms，1.01×），短序列还慢 37%
（N=256：0.081 vs 0.052 ms）。**真正的收益是显存**：N=2048 时 4.1 MB vs 532 MB，129×；
而且朴素实现在 N=4096 直接 OOM。
**证据**：同上 `rows` / `memory`。

**Q3. 短序列为什么反而慢？**
两个原因：grid 只覆盖 2 个 block，20 个 SM 大部分空闲；以及 kernel launch 的固定开销
在小 N 下摊不开。这不是实现 bug，是并行度不足。
**证据**：`_CONFIGS` 里 BLOCK_M=128 的选择，以及 N=256 与 N=4096 的 TFLOPs 差 12 倍
（1.65 vs 19.5）。

**Q4. online softmax 的三行递推，缺一行会怎样？**
`m_new = max(m_i, max(qk))`、`alpha = exp(m_i - m_new)`、`acc = acc*alpha + P@V`。
少了 `alpha` 缩放，旧累加用的就是过时的 max，权重全错。
**证据**：`triton_fa2.py::_attn_fwd_inner`。

**Q5. 序列长度不是 block 的整数倍怎么办？**
尾部块若只靠 `boundary_check` 补零，补出的零会被当成"相似度为 0 的有效 key"，
污染 softmax 分母。我用宿侧算好的 `EVEN_N` 常量分流：False 才走显式掩码，快路径不付代价。
**证据**：`triton_fa2.py` §`EVEN_N`；`tests/test_flash_attn.py` 里 N=1000/4097 两个用例。
**追问预警**：这一点我是踩过的——第一版没做，N=1000 看起来还"通过"，加 N=4097 才暴露。

**Q6. 用的 exp 还是 exp2？为什么不影响精度？**
exp2。`exp(x)=exp2(x·log2e)`，把 `log2e` 折进 `qk_scale`，省一次逐元素乘法。
精度上 fp32 累加的 exp2 与 exp 差异远小于 fp16 的舍入量级（实测误差 ≤1.95e-3）。

**Q7. BLOCK_M 为什么是 128 而不是 256？**
两条硬约束：Ada 每 SM 只有约 99 KB shared memory，`num_stages` 还要乘倍数
（D=256 + BLOCK_N=64 + stages=3 实测要 212992 B，直接 OutOfResources）；
以及 `acc` 是 `BLOCK_M×HEAD_DIM` 的 fp32，BLOCK_M 越大寄存器压力越大、occupancy 越低。
**证据**：`_CONFIGS` 的注释与 D=256 的退档配置。

**Q8. FA3 能用吗？**
不能，也无关。FA3（**arXiv:2407.08608**）依赖 Hopper 的 TMA/WGMMA/warp specialization，
H100 上 740 TFLOP/s；sm_89 没有这些指令。
（顺带：常被引作 FA3 的 2407.08691 其实是 ElasticAST，一篇音频论文。）

## 二、PagedAttention 与前缀缓存

**Q9. PagedAttention 解决了什么？**
KV cache 的碎片与不可复用。预分配方案只能按 `max_len` 要显存，
实测浪费 80.09%；分页后 0.89%，同样 2.9 GB 预算下并发序列从 26.5 涨到 133.1（5.0×）。
**证据**：`results/paged_fragmentation.json`。

**Q10. 它更快吗？**
单请求不更快。vLLM 论文 §7.1 明确写分页使 attention kernel 延迟升高 20–26%；
它赢在 batch 变大。**单请求慢 20%、并发多 5 倍，净赚** —— 这个 trade-off 要能一句话说清。

**Q11. 前缀复用的哈希为什么必须链式？**
只哈希块内 token 会让 `[A][B]` 与 `[B][A]` 撞成同一键。
链式 `h_i = H(h_{i-1}, block_i)` 让块 i 的键携带全部祖先信息，撞车就不可能。
另外**只对写满的块建索引**：没写满的内容还会变。
**证据**：`prefix_cache.py::_hash_tokens` / `get_computed_blocks`。

**Q12. 命中率 82.32% 是怎么来的？能更高吗？**
4 会话并发、共享 1024 token system prompt 的多轮对话下 82.32%。
再高不了的原因是：池子从 512 块加到 4096 块，命中率**完全不变**——
这个负载的活跃前缀集只有约 270 块，超过阈值后加显存无用。压到 128 块才降到 78.59%。
**证据**：`results/paged_prefix.json` 三行；`clamped_blocks` 字段。
**这条最容易被追问**："加显存能不能提命中率" —— 答案是不能，要改驱逐策略。

**Q13. `evict()` 有什么坑？**
把 `ref_count>0`（不可驱逐）的条目在原循环里塞回 LRU，`popitem` 会再次拿到它，
`while` 永远不结束。我第一版就是这么死循环的，而且**只在池子真的不够用时触发**——
前面所有实验都正常通过。修法是先攒进 `skipped`，循环结束再放回。
**证据**：`prefix_cache.py::evict` 注释；`docs/02` §4.1。

**Q14. 分页内核比 gather+SDPA 快多少？为什么随上下文变短而衰减？**
ctx=256 时 11.28×，ctx=2048 时 4.22×。因为 gather 路径多一次 n×D 拷贝，
上下文越长这次拷贝占比越高、加速比越低；也就是说"少搬一次"的收益快被吃干了。
**证据**：`results/paged_decode.json`。

**Q15. 你的参考实现凭什么可信？**
一开始不可信：我给它多写了一个 `permute(0,2,1,3)`，把 H 夹到 block_size 中间，
而"批量 gather"用了同样的错误顺序，两者互相印证、看起来自洽，
却与连续布局差 1.87。**一个 bug 掩盖了另一个 bug。**
正确写法是 `k_cache[ids].reshape(-1,H,D)`。现在用 fused/gather/contiguous 三路互验，3e-4。
**证据**：`docs/02` §4.2；`results/paged_correctness.json`。

## 三、MoE

**Q16. MoE 省什么？**
省权重读取，不省算力。Mixtral 47B 总参数、13B 激活；论文 §3 明说
"memory costs ∝ 47B"、"active params ∝ inference compute cost"。
**证据**：`docs/03` §1。

**Q17. 为什么你的实现在 batch=1 时更慢？**
三处，都实测：48 个 kernel vs dense 的 6 个（单次 launch 间隙最小 13.0 µs）；
gather/scatter 是随机全局访存；路由固定成本 0.391 ms，占整层 24.3%。
合计比等参数 dense 慢 4.05×。N=2048 才反超 3.37×。
**证据**：`results/moe_routing.json` 的 `kernel_counts`/`launch_gap`/`batch1_breakdown_ms`。

**Q18. 为什么始终打不过"等算力 dense"？**
因为 MoE 用 E 倍显存换的只是"在这些 token 上追平一部分算力"。
N=2048 时对等算力 dense 仍是 0.78×。要真正省算力得靠更大 batch 或 expert 并行。
**证据**：`token_sweep`/`extended_token_sweep` 的 `speedup_vs_dense_equal_flops`。

**Q19. 容量因子怎么定？**
`capacity = ceil(N/E × CF)` 是常见写法，但 top_k>1 时每 expert 平均收到 `N·k/E`，
两者差 k 倍。`N=4096,E=8,k=2,CF=1.0` 时 capacity=512 而平均需接 1024，
**即使完全均匀也丢一半**；实测丢 78.25%，而 `max_load_ratio` 只有 3.51——
说明丢弃来自公式而非不均衡。GShard 原文用 `2N/(G·E)`，那个 2 就是 top-k。
**证据**：`results/moe_balance.json` 的 `experiment_b.rows`。

**Q20. dropless 是不是一定更好？**
不是。丢弃率归零，但 71.4% 的槽位是零 pad 仍进 bmm，耗时 38.78 ms 是
有容量限制时 9.42 ms 的 4.1 倍。"不丢 token"不等于更快。
**证据**：同上表格最后一行。

**Q21. aux loss 的梯度怎么流？**
只经 `P_i`（平均 gate 概率，可导），不经 `f_i`（argmax 统计，不可导），
所以收敛是渐进的：先推高冷门专家的平均概率，下一轮 argmax 才真正转移 token。
实测 `max_load_ratio` 7.80 → 1.03（α=0.01）。
**但任务 loss 从 1.59e-4 涨到 2.14e-3（约 13 倍）——均衡不是免费的。**
**证据**：`experiment_c.runs`。

**Q22. 为什么 kernel 数不随 E 增长？**
我没写 per-expert 的 Python 循环，用 `index_add` + 一次 bmm（多余行 pad 填零），
所以 E=2/8/32 时都是 56 个 kernel。代价是 E 大时 pad 浪费——
这正是 DeepSeek 系要上 grouped GEMM 的动机。
**证据**：`expert_sweep` 的 `moe_kernels` 恒为 56。

## 四、投机解码

**Q23. 凭什么说输出分布不变？**
`Σmin(p,q) = 1 - Σmax(0,q-p)`，而 `Σmax(0,p-q)` 与 `Σmax(0,q-p)` 同为 TV 距离，
于是 `min(p,q) + max(0,p-q) = p` —— 拒绝 + 残差采样正好还原 p。
实验上：L1=0.0038（低于采样噪声下限 0.0087）、χ²=4.15（dof=7，临界 14.07）。
**证据**：`docs/04` §2；`results/spec_correctness.json`。

**Q24. 如果省掉残差修正会怎样？**
L1 从 0.0038 涨到 0.2088，χ² 从 4.15 涨到 10259。"看起来合理"的简化是错的——
这个对照比只报正确版本有说服力得多。
**证据**：`naive_no_correction` 行。

**Q25. k 是不是越大越好？**
不是。分子 `(1-α^{k+1})/(1-α)` 饱和到 `1/(1-α)`，分母 `1+k·c` 线性增长。
α=0.9/c=0.05 时最优 k=13（4.67×），到 k=32 只剩 3.73×；
α=0.8/c=0.3 时最优 k=3，k=32 时 **0.47×，比自回归还慢一倍**。
54 组配置里 53 组的 k_opt 严格小于上限。
**证据**：`results/spec_speedup.json` 的 `optimal_k` / `knee_summary`。

**Q26. 为什么它在你机器上只有 0.9–1.6×，论文是 2–3×？**
三条：（i）共享 6 GB 卡上同配置 5 次重复的极差 1.44–1.85，噪声与效应同量级；
（ii）我的实现为恢复 logits 每轮多付一次 1-token 前向，真实引擎不会；
（iii）草稿器在开放文本上接受率仅 22.9%，按公式 α=0.23 时上界本就 1.3×。
**证据**：`real_model.runs` 的 `reps_speedup_spread` 与 `predicted_speedup`。

**Q27. 那它到底什么时候有用？**
由文本可预测性决定，不由硬件。同一草稿器：散文 4.4%、结构化日志 63.8%、
JSON 66.4%、代码 91.5%，差 20 倍。所以它在代码补全/结构化输出上强，开放创作上弱——
这也解释了为什么相关论文多在代码/摘要任务上报数。
**证据**：`workload_prompt_lookup.by_segment`。

**Q28. 树状草稿的 mask 为什么不能用 tril？**
`tril` 只表达"位置在前"的因果，而树里**兄弟分支必须互相屏蔽**——
否则节点 b 会看到另一分支节点 c 的 KV，那不是"多算"，是**算错**。
必须按祖先链构造 mask：可见数 = depth + 1。
**证据**：`tree.py::tree_attention_mask`；单测 PASS（6 节点、3 分支，
3 条独立链 11 个位置合并成 6 个，省 45%）。

**Q29. 为什么 decode 阶段投机解码才划算？**
因为 decode 是 memory-bound：一次前向算 1 个还是 5 个 token，耗时基本一样
（实测比值 1.13，跨 run 落于 0.94–1.39）。prefill 是 compute-bound，
验证 k 个 token 就真的要付 k 倍算力。
**证据**：`real_model.forward_cost.ratio_by_length`。

## 五、系统级与"送命题"

**Q30. 这四个里，哪个对你的 6 GB 卡最值？**
排序：PagedAttention（并发 5.0×）> FlashAttention（显存 129×，决定能否开长上下文）
> 投机解码（看文本）> MoE（小 batch 负收益）。
理由：显存是这张卡的第一约束，而 MoE 恰恰要吃显存。

**Q31. 你这些结论换到 A100 还成立吗？**
不一定，而且我要说清哪些会翻转：
- "MoE batch=1 更慢"在 80 个 SM 的 A100 上，launch 占比会低很多，可能翻转；
- "FA 短序列落后 SDPA"同理，SM 多了并行度够，差距会缩小；
- "分页并发 5×"与显存容量强相关，大卡上相对收益下降但方向不变。
**这就是我在报告里写"有效性威胁"的原因**——单平台结论不做外推。

**Q32. 为什么不跟 vLLM 做端到端对比？**
6 GB 上构造不出有意义的并发服务负载（1.5B 权重就占 2.876 GB）。
所以我的对照是"自写朴素实现 + PyTorch SDPA"，不是工业服务系统。
这是明确的局限，不是回避。

**Q33. 你怎么保证这些数字不是编的？**
每份 `results/*.json` 带 `env`（torch/triton 版本、GPU、SM 数）与 `git sha`；
`scripts/run_all.sh` 一条命令重跑全部；正确性测试先于性能测试；
论文数字与本机数字在正文分列。**换台机器数字会变，但变化来源可追溯。**

**Q34. 你踩过最深的坑是哪个？**
三个候选，都很"静默"：
① `EVEN_N` 缺失导致尾部块补零污染 softmax（小 N 看不出）；
② 参考实现的 permute 错误与 gather 的错误互相掩盖（看起来自洽）；
③ `evict()` 死循环只在显存紧张时触发（池子够大时全部通过）。
共同点：**都没有报错，只是结果错**。所以我现在优先写"能暴露错误"的测试，
而不是"能通过"的测试。
